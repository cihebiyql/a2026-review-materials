## 1. 项目目标

本项目针对 2026 年中国研究生数学建模竞赛 A 题“通用神经网络处理器下的多核调度问题”开展建模与求解。

总体目标是在给定计算图、硬件模型和官方评估规则下，联合优化切图、核心分配和各核上的子图执行顺序，尽可能缩短整体执行 Makespan，同时控制额外数据搬运。缓存行为是需要考虑的固定硬件机制，不默认允许修改官方缓存策略。

目标还包括求解效率：算法应能在合理时间内生成合法方案。题目脚注提出避免暴力迭代搜索，单用例以5～10分钟内给出结果为佳；这不是统一规定的硬超时阈值。最终写作必须报告实际求解开销与实验预算，不能只报告方案质量。（来源：S01 §1.3、问题1脚注；S11）

仓库：<https://github.com/cihebiyql/shumo-toolkit>。写作区的仓库相对路径为 `competition/2026/A_多核调度/`。现有目录保持不变，不另建“A题_多核调度”或第二份 context。

## 2. 问题本质

本题不是单纯的负载均衡问题。性能同时受计算负载、子图依赖、跨核通信、DDR 搬运、L1/UB 容量、spill、Task 切换、Task 组织方式以及各计算/搬运 Pipe 的并行约束影响。

核心权衡是：提高并行度带来的收益，与通信、依赖等待、缓存压力及资源争用带来的代价之间的平衡。Cube 与 Vector 可在满足依赖和资源约束时并行，因此只累计各核计算量不足以描述实际执行时间。（来源：S01 §1.1–1.4、附录A/C/D）

### 2.1 我们直接控制什么

提交方案只有两个顶层字段：

- `node_to_subgraph`：每个非 `COPY_IN/COPY_OUT` 操作的子图归属。
- `core_schedules`：每个核心上的子图执行序列，同时确定核心分配。

所说的“顺序优化”首先指各核上的子图顺序。它可以影响后续核内排布，但参赛者不直接提交任意 Task 内操作调度序列。

### 2.2 官方评估流程固定什么

评估器根据方案和场景构造 Task、重建边界搬运、执行核内启发式调度、插入 spill 换入换出，并进行多 Pipe、多核、共享带宽与缓存模拟。核内局部排布时间不直接等于最终 Makespan；最终值取多核模拟所有操作完成时刻的最大值。（来源：S01 §1.4、附录B/C/D；S02）

算法研究可以使用代理或加速评估辅助搜索，但正式结果须遵循官方固定配置和评估语义；加速实现的有限样例对齐，不能自动证明其对所有方案完全等价。

### 2.3 合法性前提

方案须完整且唯一覆盖应划分的操作，sgid 为非负整数，每个子图恰好安排一次；子图依赖图必须无环，同核顺序不得违反依赖。按指定 N 核提供核心槽位，允许空槽，但不能将超出指定核数的方案混入该 N 核结果。原图是 DAG，不保证任意分组后的子图依赖图仍然是 DAG。（来源：S01 §1.3、附录B.5/D.1；S11）

输入图的直接 Op→Op 边存在题面与代码表述差异，见第7.5节，不在此自行消解。

## 3. 三个子问题

### 3.1 Problem 1：场景 A

每个子图独立构成一个 Task；Task 之间不保留核内数据，即使位于同一核心，跨 Task 数据也须经 DDR 中转。优化切图、分核和同核子图顺序，以 Makespan 为主、额外搬运为辅。

Task 激活同时受同核前序与跨核前驱约束：同核前一 Task 完成后至少等待100 cycles；跨核前驱 Task 完成后至少等待1000 cycles；激活时刻取各项约束的最大值，不将所有延迟简单累加。（来源：S01 问题1、附录D.2；S02配置）

主要难点：均衡工作量不一定形成并行；切分可能产生依赖接力和搬运，大块又可能增加缓存压力与 spill。其对具体用例的影响仍需实验验证。

### 3.2 Problem 2：场景 B

**同一核心上的全部子图合并为一个 Task，这是评估规则，不是可自由选择的融合数量。** 同核子图可在 L1/UB 中复用数据，不因同 Task 的子图边界插入搬运；跨核数据通过 COPY_OUT/COPY_IN 传递。目标 COPY_IN 在源 COPY_OUT 完成并经过500 cycles同步延迟后，才进入就绪判定。（来源：S01 问题2、附录D.2）

同核复用仍会占用 L1/UB，不能写成所有成本都为零。需要考虑驻留、spill、通信、负载及流水线约束。写作可复用问题一的通用定义并解释场景变化，但允许设计适配场景 B 的专门求解方法，不预先固定模型与算法结构。

### 3.3 Problem 3：场景 B 加共享只读 L2 Cache

沿用问题二的 Task 结构，增加全核共享的只读 FIFO Cache。COPY_IN 发射时按逻辑 tensor id 查询；命中不改变 FIFO 顺序；未命中从 DDR 读取，完成后插入 Cache，空间不足时先进先出淘汰；单张量大于 Cache 容量时不缓存。Cache 读带宽与 DDR 带宽独立。（来源：S01 问题3、附录D.5；S02第三问代码）

研究重点是在固定缓存机制下，通过切图、分核和子图顺序影响数据共享、访问时间局部性及资源争用。可以分析数据驻留和替换行为，但不能写成自行设计缓存准入、替换策略或修改官方容量。

因此，本问宜概括为“固定只读 FIFO Cache 机制下，面向数据复用的多核切图与调度优化”。

### 3.4 固定配置与指标

以下参数来自 S01 附录B.4 及 S02 的 `config.txt`；正式评估不得改动配置。

| 项目 | 固定值/口径 |
|---|---|
| L1容量 | 524288 bytes / 核 |
| UB容量 | 131072 bytes / 核 |
| DDR总带宽 | 60 bytes/cycle，所有核心的读写搬运共享，并非每核独享 |
| 场景A等待 | 同核Task切换100 cycles；跨核前驱约束1000 cycles |
| 场景B跨核拷贝同步延迟 | 500 cycles |
| 共享L2容量 | 1048576 bytes，题面称1 MB |
| L2读带宽 | 250 bytes/cycle，与DDR带宽池独立 |

主要指标与口径：

- **Makespan**：官方多核模拟的总完成时间，单位 cycles；是主要优化指标。
- **平均加速比**：逐用例计算固定启发式单核基准时间除以多核时间，再在明确的用例集合上取算术平均；不是总单核时间除以总多核时间。
- **总额外数据搬运量**：调度后全部 DDR 搬运字节数减去原图已有搬运量，是次要指标。
- **Cache命中率**：可由只读Cache服务的COPY_IN访问中，命中字节数占访问字节数的比例；不与访问次数命中率混用。
- **P3相对无L2加速比**：无L2 Makespan / 有L2 Makespan。团队实验协议要求用同一方案分别评估，以隔离缓存收益；不同方案对比须另行说明，不能将全部差异归因于缓存。
- **求解开销**：单独报告求解墙钟时间、评估次数及需要时的CPU时间；不能与方案的仿真Makespan混称“运行时间”。

前四项及第三问比值的官方要求见 S01 §1.4、各问题要求和脚注；“同方案缓存对照”及实验成本记录见 S11。

## 5. 当前已知的重要认识

### 5.1 负载均衡不是充分条件

不同核计算量接近，仍可能因强前后依赖形成接力执行。划分需同时考虑 DAG、流水线与通信，而非仅平衡工作量。此为题目机制支持的分析原则；具体用例的因果解释须有调度或对照证据。（来源：S01 §1.3及优化方向）

### 5.2 spill 不是唯一目标

减少spill可能降低搬运，但为此继续切分也可能增加重复读取、依赖等待和通信。优化目标仍以官方Makespan为核心，同时报告额外搬运，不能用spill更少直接推出方案更快。

### 5.3 超过核数的加速比需要按官方基准解释

官方单核基准是固定启发式核内调度所得结果，并非单核最优解；题目脚注明确允许出现加速比大于核数的情况。切分缩小工作集、缓解spill可能解释部分收益，但不能把所有超核数用例都归因于缓存，更不能据此宣称违反并行上限或证明算法全局最优。

### 5.4 认识的证据等级

区分题目机制、实测观察、机制假设和已证明性质。仓库报告中的“证明”“上限”“唯一有效”等措辞仍须核对前提与证据；某一候选家族的最优值不等于全部合法调度方案的全局最优值。否定某版本在某组用例的表现，不等于否定整个方法家族。（来源：S11、S12知识记录）

## 8. 写作角色分工

- **算法负责人**：算法设计、代码、实验与结果正确性说明，提供可复现的方案、配置、数据和版本。
- **写作负责人**：论文逻辑、内容组织、图表、LaTeX、结果解释与人工审核；结合团队意见明确最终采用方案。
- **Codex**：读取仓库、整理来源、起草/修改文稿、绘图制表、执行授权的核验与一致性检查，记录实际方法与范围。

Codex不能自行把报告数字或推断宣布为最终事实，也不能擅自选择最终论文算法。但可以按协作规则完成证据核验并留下记录，不把所有可通过文件和计算解决的问题都交回人工。结果核验与文稿人工审核分开管理。
